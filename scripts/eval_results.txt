Commands
----------------------------------------------------------------------

  plain, 1 run
    python scripts/eval_retrieval.py --top-k 5 --backend http://localhost:3001

  rewrite, 4 runs
    python scripts/eval_retrieval.py --top-k 5 --backend http://localhost:3001 \
      --rewrite --sleep 4

  decompose, 3 runs
    kubectl cp scripts/eval_retrieval.py casetally/<api-pod>:/tmp/eval_retrieval.py
    kubectl exec -n casetally <api-pod> -- sh -c \
      'cd /app && PYTHONPATH=/app python3 /tmp/eval_retrieval.py --mode decompose --runs 3'

The first two modes go over HTTP to /v1/search through a kubectl port-forward. The
decompose mode runs the answer path's retrieval in-process inside the API pod, because
no endpoint exposes decomposition without also generating an answer. It generates no
answers. Its fused ranking is scored on the same top-5 slice the other two modes score,
so the three sets of columns are comparable.

Why the run counts differ
----------------------------------------------------------------------

Plain hybrid search performs no LLM call, is deterministic, and reproduces exactly, so
one run is enough. Rewrite and decompose each call an LLM before retrieving. An LLM call
is not reproducible even at temperature 0: the serving backend configuration is not
fixed, and batched inference on a mixture-of-experts model is not bit-reproducible.
Temperature 0 means greedy, not deterministic. So those two modes are reported as means
over several runs, with every per-run value and the spread listed, and re-running this
file will not reproduce them digit for digit. Treat any single run of them as one sample.

Em dashes in the harness output have been normalised to plain punctuation here.

NOTES FROM THIS MEASUREMENT
======================================================================

Decomposition stability: 14 of 19 queries produced identical sub-queries in
all 3 runs. The rest varied, which is why this mode is reported as a mean.

Sub-queries produced per question: [3] (the prompt allows 3 or 4).

Precision@3 is partly capped by construction for decomposition. It always divides by 3,
while a fused multi-issue ranking deliberately interleaves issues, so when only one of
three issues maps to the expected title the metric cannot exceed about 0.33 however good
retrieval is. MRR and the titles row do not have that problem.

Relevance is scored by U.S. Code title number, which is coarse. Titles 42 and 29 are
large, so a pension section in Title 29 counts as relevant for an unfair dismissal
question. The employment group is a regression tripwire, not a quality measure, and at 4
queries every single query moves its mean by 0.25.

Latency is not comparable across modes. Plain and rewrite are server-reported took_ms
over a port-forward for one search. Decompose is wall time for 3 concurrent searches
in-process, and excludes the decompose LLM call that precedes them.

Prior baseline, for reference: an earlier run against 22 of 53 titles (32,969 chunks)
scored P@3 0.31, R@5 0.34, MRR 0.39, with 7 queries at 0.00 purely because their titles
were absent from the corpus.

Commands
--------------------------------------------------------------------------

  plain, once per session
    python scripts/eval_retrieval.py --top-k 5 --backend http://localhost:3001

  rewrite, 4 runs per session, 8 pooled
    python scripts/eval_retrieval.py --top-k 5 --backend http://localhost:3001 \
      --rewrite --sleep 4

  decompose, 3 runs per session, 6 pooled
    kubectl cp scripts/eval_retrieval.py casetally/<api-pod>:/tmp/eval_retrieval.py
    kubectl exec -n casetally <api-pod> -- sh -c \
      'cd /app && PYTHONPATH=/app python3 /tmp/eval_retrieval.py --mode decompose --runs 3'

The first two modes go over HTTP to /v1/search through a kubectl port-forward. The
decompose mode runs the answer path's retrieval in-process inside the API pod, because
no endpoint exposes decomposition without also generating an answer. It generates no
answers. Its fused ranking is scored on the same top-5 slice the other two modes score,
so the three sets of columns are comparable.

Why the run counts differ
--------------------------------------------------------------------------

Plain hybrid search performs no LLM call and is deterministic. It returned identical
numbers in both sessions, every metric and every context fraction, which is what makes
it usable as the baseline the other two are measured against. It is therefore reported
once rather than pooled.

Rewrite and decompose each call an LLM before retrieving. An LLM call is not
reproducible even at temperature 0: the serving backend configuration is not fixed, and
batched inference on a mixture-of-experts model is not bit-reproducible. Temperature 0
means greedy, not deterministic. Their figures are means over every run with the range
across runs beside them, and a single run of either is one sample rather than a
measurement. Re-running will not reproduce them digit for digit.

two sessions, so this group cannot rank them against each other. What it does show is
that both beat plain search: all 14 LLM runs scored above plain's 0.38, lowest 0.62. And

no claim is made that decomposition retrieves better context on statute-phrased queries.

concurrent searches in-process, excluding the decompose LLM call that precedes them. The
README quotes session 1: plain p50 26ms and p95 105ms, rewrite 72ms and 160ms,
decompose 256ms and 471ms.

NOTES
==========================================================================

Decomposition stability: within a session, 12 of 19 queries produced identical
sub-queries across its 3 runs in session 1 and 14 of 19 in session 2. The rest varied.

Precision@3 is partly capped by construction for decomposition. It always divides by 3,
while a fused multi-issue ranking deliberately interleaves issues, so when only one of
three issues maps to the expected title the metric cannot exceed about 0.33 however good
retrieval is. MRR and the titles row do not have that problem.

Relevance is scored by U.S. Code title number, which is coarse. Titles 42 and 29 are
large, so a pension section in Title 29 counts as relevant for an unfair dismissal
question. The employment group is a regression tripwire, not a quality measure, and at 4
queries every single query moves its mean by 0.25.

Em dashes in the harness output have been normalised to plain punctuation. The harness
itself no longer emits them, so later regenerations need no normalising.

Prior baseline, for reference: an earlier run against 22 of 53 titles (32,969 chunks)
scored P@3 0.31, R@5 0.34, MRR 0.39, with 7 queries at 0.00 purely because their titles
were absent from the corpus.
